# ZCode Android shell — scope and acceptance

## Product boundary

`mobile/android` is an independent Android application (`io.github.xhwxt.zcodemobile`) named **ZCode**, version `0.1.3` (versionCode 25; the version line was reset to 0.1.0 and increments only its last digit). It provides a native add-device form, a multi-device list, a secure Android `WebView` container for already-issued ZCode links, **first-party pairing** (a native dialog that redeems a one-time code through `POST /api/pairing/redeem`), and **session renewal** (`POST /api/auth/renew`) driven by a long-lived per-device credential held in the Android Keystore. It does not implement endpoint discovery, a general JavaScript bridge, downloads, or native business UI; it owns no *application* logic (conversation/workspace/session state stays in the page). The accepted entry URLs are HTTPS `/?token=…`, `/web-remote?remoteControlToken=…`, and the credential-less entries `https://host/` (bare origin, the form used once a device is paired) and `/api/pairing/page`; their authentication query and fragment are retained for the Web application.

## State owners

- Native app: validates entry URLs, stores multiple devices (metadata plaintext, links Keystore-encrypted), owns the device list / add-device / error screens, the file-picker lifecycle, the shell palette — which follows the **page** theme (zai-dark/zai-light), never the OS day/night setting — and, since v0.6, the **per-device credential** (one non-exportable Keystore AES-GCM key per device slot) plus the session it mints from it. The credential itself is never persisted outside the Keystore; the short-lived session token is never persisted at all.
- Android platform/WebView: owns TLS trust, cookies, DOM storage, service workers, IME, document selection, and lifecycle. The shell never refreshes or reloads page state on resume/configuration changes.
- ZCode Web UI/server: owns all application state and authentication semantics. The shell never reads a credential out of the page, never puts one in a URL, and never transforms the entry URL; the only credentials it handles are the device credential it holds in the Keystore and the session cookies it injects into the WebView cookie jar.

## Security and interaction boundaries

- Reject malformed, non-HTTPS, user-info, unsupported page types, invalid ports, wrong/duplicate credential parameters, and unsafe schemes without echoing the supplied URL or credential in errors/logs/titles.
- Same-origin navigation stays in the WebView. Only a user-initiated external HTTPS navigation may reach Android after a host-only confirmation; credential-bearing external URLs and unsafe schemes are rejected. Every TLS error cancels. Cleartext, file/content URLs, and mixed content are disabled. No `addJavascriptInterface`; the page can only post one-way messages upward (console prefix + origin-restricted WebMessageListener).
- The link is never placed into instance state, intent extras, logs, or titles; backup excludes all device data; Keystore failure surfaces as a recovery message, never a crash and never a plaintext fallback.
- Web popups and permissions are denied. File uploads use `ACTION_OPEN_DOCUMENT`; pending callbacks are invalidated when the connection changes. Downloads are not handled in-app: a download request hands the HTTPS URL to the system browser (which owns downloading); non-HTTPS targets surface the "不支持下载" notice.
- Back: IME first; same-origin WebView history second; otherwise the task goes to background — never a reload.

## Acceptance

1. An independent Gradle project at `mobile/android` (AGP 8.10.1 / Kotlin 2.1.0 / Gradle 8.11.1 wrapper with pinned checksum; bounded memory/workers), package/version as stated above.
2. Pure JVM tests cover accepted URL shapes, malformed URI, user-info, port boundaries, origin/similar-host decisions, external credential links, HTTP rejection, query encoding, and safe-navigation decisions.
3. The app has a designed multi-device list (cards, status dot, per-row actions, empty state), an add-device form, encrypted multi-device persistence, safe WebView settings/clients, the upload-picker lifecycle, rotation/resume behavior, renderer recovery with a draft-loss notice, and an explicit download limitation.
4. The shell palette and status-bar strip follow the live page theme via the dual signalling channel, applied in code (never through a runtime theme switch, which would reuse themed drawables cached under the previous palette); long-pressing the page's left-panel control opens the device list.
5. A slow or stalled first load never traps the user: a native connecting overlay offers the device list and degrades to the error screen after a timeout; back from an unloaded page leads to the device list. WebView algorithmic darkening is disabled so the page's own theme (including "follow system") stays authoritative.
6. Task notifications: the page asks for a notification when a task finishes while it is unfocused, but Android WebView has no Web Notifications API. The shell installs a document-start shim for `window.Notification` (and binds `document.hasFocus()` to `document.hidden`, matching dsh-mobile's visibility-based notifier) and posts the payload through a native `NotificationChannel`. The OS permission is requested only from a visible screen, bounded to the platform's own prompt limit; a channel switched off in system settings counts as unavailable.
7. Keep-alive status row (v0.6.x): the foreground service's summary line combines the page-reported task counters with the probe loop's connection state, priority order: running tasks → probe disconnected (2+ consecutive failures) → no credential → completed-unread → idle. The page reports `task-started` / `task-finished` (parameterless, incremental — each delivered exactly once through the single-transport `post()`, which prefers the WebMessage object and only falls back to the console prefix) and `tasks-consumed` resets the completed figure. The shell zeroes the running count at every main-document start, so a reconnecting page re-asserts without double-counting. Probe-target failures (device store, keystore, link validation, empty token) each log one diagnostic `Log.d` line (no token/link values) and surface as the "未配对或凭据失效" summary text; network failures surface as "连接断开，重试中". The FGS cannot learn about task completion while the page is frozen or dead — background completion notifications beyond the shim's reach require a server-side pending-count endpoint (known boundary, see README).
8. README documents build/test/sign/distribution truthfully and distinguishes host-test evidence from device-only checks. No build/pull/merge of the Web UI and no writes outside `<repo>/mobile`.
9. Historical limitation, now closed: sessions invalidated by a server restart while the app is open are healed server-side (silent session re-issuance from the long-lived renewal cookie injected by the shell) plus the page's soft-reconnect 401 handling; the user no longer needs to leave and re-enter the device.
10. Known boundary: the keep-alive FGS only *keeps the process alive*; it cannot observe task state (no task-status endpoint is exposed to the device credential, and the probe path only answers reachability/instanceId). Completed-task notifications therefore still originate from the page; when the WebView is frozen or the process was restarted in the background, the notification for that completion is lost until the user reopens the app (the status row's counters survive via SharedPreferences).
11. Probe credential source (v0.1.3): the keep-alive probe prefers `ProbeTargetCache` — the (deviceToken, origin) pair the page flow verified at connect/renew/pair time, held in process memory only (never in prefs, never logged) and invalidated on `dropCredential` and on a probe 401 (REVOKED). Only when the cache is empty (cold FGS start before the page connects) does the probe fall back to the per-tick store chain (DeviceStore → linkOf → link validation → Keystore decrypt), so a transient Keystore failure can no longer make the status row claim "未配对或凭据失效" while the page's memory-held credential keeps chat working.
12. Text-selection guard (v0.1.3): while the WebView's selection ActionMode is up (tracked via `onActionModeStarted`/`onActionModeFinished`), `routeMainFrameTarget` refuses the shell's external-link confirmation on the main WebView so the system selection menu (复制/分享) keeps operating; normal taps are unaffected because the selection menu is dismissed by then. The 0.1.2 download-listener hand-off to the system browser is untouched.
